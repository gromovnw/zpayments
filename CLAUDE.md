# CLAUDE.md

Памятка для ИИ-ассистента, впервые открывающего этот репозиторий. Коротко: это Bukkit-плагин, живущий на чужих Minecraft-серверах, который раз в N секунд спрашивает у API магазина "что мне выдать" и выполняет консольные команды. Никакой бизнес-логики (цены, каталог, оплата) здесь нет и быть не должно.

Бэкенд, с которым плагин говорит по HTTP — отдельный закрытый проект, его код и структура сюда не относятся. Всё, что нужно знать о протоколе — ниже, и оно ограничено тем, что и так видно в этом самом коде (`ShopApiClient`, `http/dto/*`).

## Контракт с API (как его видит сам плагин)

- `GET /api/plugin/purchases/pending` → `{ orders: [{ orderId, nickname, total, items: [{title,count,price}], tasks: [{key,command}] }] }`
- `POST /api/plugin/purchases/{orderId}/ack` ← `{ key, success, output }` → `{ ok, orderId, status }`
- Заголовки авторизации: `X-Shop-Id`, `X-Server-Id`, `X-Plugin-Key` (см. `ShopApiClient.openConnection`).

Если меняешь формат — оба конца (плагин и API) должны обновиться синхронно, иначе опрос начнёт молча возвращать пустой список или падать с ошибкой авторизации. Gson десериализует DTO по точному совпадению имён полей (без `@SerializedName`), так что имя в Java обязано буквально совпадать с JSON-ключом. И держи в уме обратную совместимость: на серверах в проде уже стоят старые версии джарника, которые не обновятся мгновенно — ломающее изменение контракта без версионирования тихо выключит доставку у части магазинов.

## Архитектурные решения, которые НЕ случайны

- **Полинг, не вебхук/RCON.** Сервер с плагином не обязан быть доступен снаружи вообще — ни открытого порта, ни статического IP. Это осознанный компромисс: задержка до `polling.request-delay-seconds` (по умолчанию 20с) взамен нулевой поверхности атаки на стороне игрового сервера. Не предлагай "заменить на вебхук" — это ломает главное преимущество перед RCON-доставкой.
- **Main thread vs async — это не стиль, а требование Bukkit API.** `ShopApiServiceImpl.enable()` крутит опрос на `runTaskTimerAsynchronously` (сетевой I/O не должен блокировать тик сервера), но `Bukkit.getPluginManager().callEvent(...)` и любые Bukkit-команды/инвентари обязаны выполняться на главном потоке — иначе Paper бросает `IllegalStateException`, а на Spigot тише, но так же небезопасно. Отсюда `SchedulerUtil.runOnMain(...)` перед каждым вызовом `callEvent`/`ConsoleCommandExecutor.execute` в `CartServiceImpl`. Если добавляешь новый путь выполнения команды — заверни его так же.
- **Дедупликация двойная и намеренно.** `storageService.hasEntry(orderId, key)` (переживает рестарт сервера) + `inFlight`-сет в `CartServiceImpl` (защита от гонки внутри одного цикла опроса, до того как ack успел долететь). Один без другого не спасает: только storage — не защищает от двух одновременных вызовов `process()` за один опрос; только in-flight — не защищает от повторной выдачи после рестарта до получения ack.
- **`ConsoleCommandExecutor` — Proxy вокруг `ConsoleCommandSender`.** Нужен не для декорации, а чтобы ПЕРЕХВАТИТЬ текст, который команда пишет через `sendMessage`, и отправить его назад в `ack` как `output`. Метод `execute()` — `synchronized`, потому что HANDLER общий (статический) на весь плагин: параллельный вызов на другом потоке перепутает вывод разных команд. Если понадобится параллельное исполнение — нужен НЕ статический хендлер, а новый на каждый вызов.
- **Shade + relocation в `pom.xml`.** `eu.okaeri`, `com.j256.ormlite`, `com.google.gson` релоцируются в `it.gromov.zpayments.libs.*`. Стандартная защита от конфликта версий с другими плагинами на том же сервере, использующими те же библиотеки — не убирать ради "чистоты".
- **Java 8 target, Spigot API 1.12.2 (без NMS).** Осознанно широкая совместимость (см. комментарий в `plugin.yml`) — не поднимай `java.version`/API-версию без явного запроса.
- **Okaeri `NameStrategy.HYPHEN_CASE`** на всех конфиг-классах — поля вида `requestDelaySeconds` в YAML превращаются в `request-delay-seconds`. Название поля в Java и ключ в `config.yml` — РАЗНЫЕ строки.
- **`config.yml`/`messages.yml`/`menu.yml` не лежат в `src/main/resources`.** Они не статические шаблоны — Okaeri генерирует их на лету из аннотированных дефолтов Java-классов (`ConfigServiceImpl`, `MessagesConfig`, `MenuConfig`) при первом запуске. Если нужно поменять дефолтное значение — меняй Java-поле.

## Чего здесь специально нет

- Каталога товаров, цен, скидок — плагин получает уже готовую команду для выполнения, не решает "что почём".
- RCON-клиента — это отдельный способ доставки, плагин ему не обёртка.
- Хранения платёжных данных/секретов покупателя — плагин видит только `X-Plugin-Key` и текст команд.
